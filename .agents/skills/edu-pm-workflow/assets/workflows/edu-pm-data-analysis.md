# PM数据分析报告工作流

本工作流协助产品经理在功能上线后，快速将原始业务数据转化为结构化、可视化的分析报告，进行漏斗诊断、异常归因，并输出下一步迭代建议。

## 适用场景
- 新功能上线首周/首月的数据复盘
- A/B 测试结果分析
- 日常核心指标监控分析

## 需求目录与档案（落盘前必读）
先确定产品项目根目录，读取 `.agents/references/requirement-record.md`，按 `requirement_id` 找到已有需求。独立分析专题也可首次运行 `python3 scripts/pm_requirement.py --project <产品项目根> --name <专题名>`。档案父目录称 `REQ_DIR`；报告存入 `REQ_DIR/数据分析/`。项目可用 `pm-forge.json` 配置项目内 `artifact_root`；下文 `{需求名称}/` 均指 `REQ_DIR`。

## 执行步骤

### Step 1: 收集原始数据
1. 接收用户提供的数据源。数据形式可以是：
   - 粘贴的 CSV/Excel 文本数据
   - 业务 BI 看板的截图（需 AI 视觉解析）
   - 用户口述的几个核心关键指标
2. 确认分析的周期（日/周/月）和核心关注点。
3. 记录数据来源、提取时间、统计范围和缺失值；从档案 `metrics[]` 读取既定指标、口径、基线与目标。无原始数据时只提供分析计划，不生成虚构的上线表现。

### Step 2: 数据结构化与诊断分析
1. **指标概览**：依据已有 `M-*` 指标的统计口径计算结果并与基线、目标比较；没有基线或目标时标为待确认，不推断涨跌幅。
2. **转化漏斗**：梳理用户核心路径流转率，定位断点。
3. **异常归因**：针对偏低或暴跌的指标，结合业务逻辑推导可能的原因（例如：功能隐藏太深、定价门槛过高、UI引导弱）。
4. **专项分析**（可选）：针对不同人群（角色/渠道/地区/机型）的交叉分析。

### Step 3: 结果回流与下一步决定
- 把实际结果、时间窗口、数据来源写回档案相应 `metrics[]`。结论区分“观察到的事实”和“可能原因”；样本不足时记录限制。
- 在证据足够时记录 `decisions[]`：继续、迭代或停止，引用 `M-*` / `SRC-*`，并说明下一步动作。没有充分证据时将判断列入 `open_questions`，不标记为已完成闭环。

### Step 4: 生成《数据分析报告》HTML
1. 产物按需求名分文件夹：在 `{需求名称}/数据分析/` 子目录中创建 HTML 报告（该需求顶层目录不存在则先创建）。
2. 文件命名规范：`{需求名称}/数据分析/{需求名称}-数据分析.html`。
3. **UI 规范**：
   - 采用专业数据 BI 工具的暗黑主题（深蓝/黑背景，高亮重点色）。
   - **核心卡片**：顶部展示有来源的 KPI 数值及其口径；无可比基线时不显示涨跌幅。
   - **可视化图表**：使用原生 SVG 或轻量级图表库（如 ECharts 概念模拟的纯 CSS/SVG）展示趋势折线图、柱状图。
   - **漏斗图**：CSS 绘制的转化漏斗进度条。
   - **洞察模块**：用高亮卡片突出“异常流失”或“超预期”的发现。
   - **行动项**：底部清晰列出下一步迭代计划。
4. 将报告路径写入档案 `artifacts.analysis`；只有取得真实结果时才将 `stage` 更新为 `measured`。

## 输出交付物
- 沉浸式数据分析报告 (`{需求名称}/数据分析/{需求名称}-数据分析.html`)
